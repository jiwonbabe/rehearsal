# Notes (assumptions, one line each)
- Spark cache is keyed by call name (directions-m1, directions-m2, adversary-<id>), not by prompt hash: files are committed and hand-editable.
- Shock codes outside the catalog are dropped by engine.CleanCombos; spark.ParseShocks only extracts the lists.
- Server handlers share one mutex via locked(); /api/setup does not recalibrate rates, it only changes budget/goal/target/market.
- sparkcache builds the month-1 planner summary from the weeks before October (pre-review view); month 2 adds the October review block. Engine rates in the server are always calibrated on the full data.
- spark/cache/*.json were generated live on Nov 2, 2026 with muse-spark-1.3 via `go run ./cmd/sparkcache` (api.meta.ai/v1). Two prompt rules were added to prompts/directions.md so ranges reach what the budget allows; without them Spark anchored creator_count to the 2-3 the brand had tried and no flip existed.
- Live month-1 directions include a `mix` direction; the demo picks pay_for_reach + send_to_creators.
- Docker CLI is installed but its daemon was not running, so the Dockerfile was not smoke-tested; run the build command in DEMO.md before relying on it.
- Fly CLI (fly/flyctl) is not installed, so nothing was deployed; the two deploy commands are at the top of DEMO.md and README's Live line says "Deploy: see DEMO.md".
- Server is cache-only: main() unsets MUSE_API_KEY so the demo never calls Spark live; cmd/sparkcache is the only live caller.
- The profile read is cached by handle (spark/cache/profile-<handle>.json): the same handle returns the same read regardless of the image sent.
- /api/profile takes `source`; only "screenshot" exists. Instagram Login (Graph API) will add `source: "instagram"` with the same prompt and ValidateProfile after Meta App Review.

- Success metric revenue is display-only (goal ÷ avg price); the engine tests orders.
- spark/cache/playbook-<id>.json generated live on Nov 3, 2026 (Spark role 5, prompts/playbook.md) from the cached profile read + brand basics; one file per direction id, month 2 reuses it.
- Creator fit read (Spark role 6, prompts/creator.md) is cached by handle in spark/cache/creator-<handle>.json; the demo server has none until screenshots are dropped into web/demo-creators/<handle>.png and sparkcache is rerun.
- Launch numbers: creator_dms = creator_count × 2 (assume half reply); ads daily budget = ads_usd / 28 days; posts per type by largest remainder of posts_per_week × mix.
- Meta ads adapter creates campaign + ad set only (OUTCOME_TRAFFIC + LINK_CLICKS, no pixel; not yet tried against a real ad account); the owner picks the boosted posts in Ads Manager. META_* env vars are read per request; MUSE_API_KEY stays unset in the server.
- Meta data is mock (data/meta/wrenfield.jewelry, data/meta_mock.py seed 7) shaped like the Graph API; post_type labels on media would come from Spark vision in live mode. Orders by channel need the shop; link taps are the proxy.
- platform_stats.json holds only numbers found in sources checked on Nov 3, 2026 (3 rows); no automatic refresh. Channel verdicts are reasoned, not stress-tested, and the card says so.
- Korean: Spark translated each cache file once (spark/cache/ko/); static copy is a dictionary in web/i18n.js applied by a MutationObserver, so a string missing from the dictionary stays English rather than breaking.
- Trust card shows the holdout backtest (rates from the first 39 weeks, tested on the last 13) as the headline; in-sample is a footnote. Known-answer table compares calibrated rates to data/synthetic.py constants written into brand.json as generator_truth (engine never reads it to calibrate). eng_per_post truth is scaled by average followers / 4000; seed_post_rate differs on purpose (planted October no-show).
- Mock Meta account is @demo.brand (fictional): the demo brand @wrenfield.jewelry is fictional too, so no real account's numbers appear anywhere. Provenance chips: Real · your screenshot / Demo input / Engine · synthetic brand data.
- Seasonal prior is US jewelry only (data/seasonality.json) and applies to plans with a month; October's review plan has month 0 so the review is unchanged. Demo month 1 = November (1.04 / 1.18), month 2 = December (2.23 / 1.27). Two fallback combos were swapped for season_flat so the baseline can die in December.
- Verified against a real ad account on Nov 3, 2026: delivery_estimate returns MAU bounds only (no DAU); campaign creation needs is_adset_budget_sharing_enabled, ad set creation needs targeting_automation.advantage_audience (0 = exact audience) and a start_time not in the past. A paused campaign + ad set were created and left paused for the demo; delete them in Ads Manager afterwards.
- Tester round (Nov 3 evening): the committed plan now carries its title and month (Launch warns when the app has moved to another month); Directions persists selection on every click and explains a third pick; Setup flags unsaved edits, remembers the last profile read, shows errors inline; Verdict shows each paid plan's gap over the baseline (engine BaselineGaps: extra orders in a bad month and $ per extra order) and softens the headline when the gap is ≤ 2 orders; ranges are whole numbers; trust tables and the channel grid are collapsed by default; /setup.html redirects home.
- Month-sized goal (SeasonGoal = goal × demand, half-up) is offered, never applied silently: the owner clicks it on Directions or Verdict. At 46 the December baseline survives 18/20; at 103 ads 8/20, seeding 3/20, baseline 1/20.
- Review's button names the next month to plan (server: SeasonFor month 2); a channel line with no number gets a grey "No data" chip instead of "Your data"; Review and the month-2 "what October taught" range are whole numbers like Verdict. Directions preselection is not a feature: a card opens selected only because the tab's last selection persists (cleared when a month is applied).
- The month-sized goal is offered once: "Use N for <month>" sends goal_month and the server stops offering for that month (a goal typed on Setup is offered again). The card says "If N is your average-month goal" because the app cannot know whether the owner's number already accounts for the season.
- Demo brand is fictional: Wrenfield Jewelry, @wrenfield.jewelry (Portland, OR; mock profile screenshot rendered from HTML in web/demo-posts/). Nothing in the demo is a real account. Naver blog left the channel enum (US demo). profile-wrenfield.jewelry.json (en + ko) and the Naver-free playbook/channel sentences were hand-edited on Nov 3 because the Muse key was not in the shell; regenerate with `MUSE_API_KEY=... go run ./cmd/sparkcache` after deleting those cache files.
- Seasonality freshness (checked Nov 3, 2026): Census suppresses jewelry-store monthly sales from March 2021 ((S) in every later sheet of mrtssales92-present.xlsx), so 2017-2019 is the latest jewelry-specific pattern; the parent category 448 for 2023-2025 shows the same shape (Dec 1.56×, Nov 1.12-1.16×, Jan 0.73-0.75×) as 2019, so the prior was kept and the cross-check is written into the source line. Ad cost: Gupta 2024-2025 is the latest full-year monthly series; AdKit 2026 (Jan-Sep, worldwide medians) is partial and not normalizable to a year.
- Seasonality is per category (data/seasonality.py → data/seasonality.json from data/census/mrtssales92-present.xlsx, 2023-2025; jewelry 2017-2019 because Census suppresses it later). Setup has "What you sell"; /api/setup {category} swaps the table and an unknown key is 400. The cached Spark season note quotes the jewelry indexes, so for another category the note is dropped by validation (the numbers and sources still show).
- Jewelry demand index (Nov 4): still Census 2017-2019 months (the only jewelry-specific monthly series; BEA's monthly jewelry PCE is seasonally adjusted, Census suppresses the line after Feb 2021, Mastercard/Adobe publish no monthly jewelry levels). Checked against Signet Jewelers' reported FY2025-FY2026 quarterly sales: Q4 (Nov-Jan) 1.39 vs this table's 1.32, Q1-Q3 within 0.05, so the shape was kept rather than rescaled (a 1.04→1.10 November change is inside the method's noise and would only reshuffle the demo's November numbers). The check is written into the card's source line.
- Lever coverage (Nov 4): LeverCoverage counts weeks with ads / creators / a sale; <6 weeks = thin (warning on Verdict cards and the trust card), 0 weeks = none (the direction is marked Not rated, the Verdict card shows no survived count or gap: Calibrate would otherwise read 0 ÷ 0 as "no effect"). Go + Python + fixture coverage.json.
- Creator pool (Nov 4): after a Meta connect the engine counts seeded creators as consecutive members of the creators-found pool (followers × engagement rate relative to the pool mean), with a different starting creator for every bad month, so the mean stays calibrated to history and the spread comes from the creators' real audience sizes. History never uses the pool. Fixture creator_pool.json. The November flip moved 0.88 → 0.90; the cached check line's quoted figure was updated by hand (regenerate with sparkcache).
